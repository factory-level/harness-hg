The rehearsal proved the fleet was not rebuildable

The first honest run of the recovery gate failed at the rebuild, on a credential somebody had created by hand weeks earlier. The fleet had not been rebuildable since that day — and everything was green the entire time.

There is a difference between a restore rehearsal and a recovery rehearsal, and it comes down to one line: whether you delete the local scaffold before you restore. Until you do, you are testing that a backup can be unpacked. Once you do, you are testing the claim that actually matters — that the fleet can be rebuilt from what you kept.

I moved that line and ran the whole thing end to end for the first time. It failed at the rebuild.

The bundle pod sat in Init:0/1 for fifteen minutes, waiting on a repository credential that did not exist. That credential had only ever existed because, at some point weeks earlier, an operator created it by hand to get past a problem in the moment.

A credential created by hand is not declared state.

Which means the fleet had not been rebuildable since the day that command was run. Nothing said so. It was genuinely healthy the entire time — right up until something deleted the cluster, which is the only moment the claim is ever tested, and the worst possible moment to discover it was false.

That is precisely what the gate exists to test, and the first honest run of it found the claim was false. I want to be careful about how satisfying that is to write versus how it should read: a gate that finds nothing on its first run has usually not been pointed at anything real.

What shipped, and what deliberately did not

hg up now creates an empty placeholder for any bundle repository credential that has none. It does not make a private clone work, and that is the entire point of it. It converts a pod hanging forever on a mount error that nothing surfaces and nobody is watching into a failure that arrives at apply time, loudly, where a human is already looking. A real credential is never overwritten.

That is a smaller fix than the problem deserves, so I logged the real one instead of pretending otherwise: the key has to arrive through the declared secret path like every other credential does. And there is a posture question underneath it I would rather answer deliberately than by accident — whether up should refuse outright rather than write a placeholder at all. Refusing is more honest and worse to use. I have not decided, and the issue says so.

The shape this keeps taking

This is not the first time the same lesson has arrived on this project. The interesting failures are almost never in the code you wrote. They are in the state somebody created outside it, which by definition no test covers, because no declaration mentions it.

It is also why "a backup exists" and "a restore worked" are two different words on every surface this thing has — the CLI, the fleet view, the Grafana panels. A backup is available when it uploads and restorable only once a restore has actually run against it. A fleet with nightly uploads and no restore runs displays restorable: never, and it reads as alarming precisely because it is.
