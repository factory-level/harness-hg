Bundling is a co-location decision, not a security one

The same asymmetry turned up three separate times before I named it. Moving two agents into a bundle to save resources was quietly removing the ability to isolate them.

Bundles exist for a boring reason. Running one pod for two small agents costs less than running two. It is a resource decision, and it should be nothing more than a resource decision.

Three times, in three unrelated reviews, I found that it had become more than that.

  • Backups. Routine coverage resolved against a profile's own namespace, so a bundled agent read as uncovered when it was not.
  • Namespace resolution in hg backup. Same shape, different surface, found separately.
  • Network policy. The profile chart had carried an opt-in NetworkPolicy since the pod provider landed. The bundle chart had none at all — so moving two agents into a bundle silently removed the option to isolate them.

Individually, each of those reads as a small bug worth a small fix. Together they are one design defect: a feature added for efficiency inherited none of the guarantees of the thing it replaced, and nothing in the system knew the two were meant to be equivalent.

Bundling is a co-location decision. It must never be a security downgrade.

The third instance is when you stop fixing instances and write the rule down.

What shipped

The bundle chart got its NetworkPolicy. Off by default — the same default the profile chart uses, and for the same honest reason: on a cluster whose network plugin does not enforce policy, an enabled-by-default policy would look like protection while being nothing at all. A security control that lies about itself is worse than one you know you have not switched on.

When it is on, it admits exactly the ports the members declare, and a render test fails if any declared port is missing from the rendered policy. A policy that quietly severs a member's listener is worse than no policy — you would spend a day debugging the agent before suspecting the thing that was supposed to be protecting it.

The same pull request gave the bundle chart its first tests at all, which tells you something about how the feature arrived in the first place.

Why this one is written down

Not because a NetworkPolicy is interesting. Because the efficient variant must inherit every guarantee of the thing it replaces is a rule I now apply to any feature whose entire justification is saving resources — and I did not have that rule three weeks ago. It cost three bugs that all looked unrelated to acquire it.

It generalises past this project. Any time you offer a cheaper path alongside a safe one, the cheaper path is where the guarantees quietly go missing, because nobody re-derives them — they assume the two variants are the same thing wearing different clothes.
